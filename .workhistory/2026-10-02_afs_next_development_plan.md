# 폭 대조 실험 중단 후 AFS 다음 개발 제안

2026-10-02 UTC. 사용자는 이번 실험을 이 정도에서 멈추고 다음 작업을 물었다.
3.2m timeout 재실행을 선행 조건으로 삼지 않는다. 이번 턴은 다음 범위 검토와 기록이며
코드 구현이나 새 유료 실행에 대한 승인을 받은 것으로 해석하지 않는다.

## 보존할 현재 결과

이번 개발 suite의 신규 실행은 4.0m PASS, 3.6m PASS, 3.2m INCONCLUSIVE다.
기존 성공까지 합치면 4.0m 성공 3회, 3.6m 성공 1회다. 3.2m를 FAIL로 바꾸거나
성공/실패 경계를 선언하지 않는다. 원본 suite는 NEEDS_ATTENTION이며 이 턴에서는
DB를 닫거나 상태를 바꾸지 않았다. 원본과 누락 비용을 포함한 이력을 그대로 보존한다.

## 코드에서 확인한 기존 기능과 다음 확장점

`AFS_SEARCH_V2.md`와 `afs_contrast.py`, CLI를 읽었다. 행동 요약, 가설 우선순위,
유사 실패 억제, 성공/실패 메모리, 혼합 반복·관측 경계 선택, LLM 제안 연결, 회귀 자산은
이미 있다. 따라서 다음 작업을 이 기능들의 최초 구현으로 표현하지 않는다.

반면 현재 개발 대조의 `next`는 COMPLETE이고 제외가 없는 suite만 받는다. 이력
입력도 VALID만 허용한다. 현 가설 선택은 지정된 기준 장면 중심이며, LLM이 비교 가능한
과거 장면 중 기준점을 자유롭게 선택하는 확장은 기존 문서에도 후속으로 남아 있다.
현재 source lock과 결과 검증을 무시하고 이 중단 suite의 next를 강제로 실행하지 않는다.

권장 다음 범위는 **근거에 연결된 기준 장면 선택과 여러 환경 축의 가설 선택**이다.
로봇은 고정하고 기존 구성 요소를 재사용한다. 이는 단일 통로 폭 반복이나 새 점프·조작
기술 개발을 이어가는 제안이 아니다.

## 제안하는 구현 순서

1. 검토한 이력을 명시적으로 가져오는 새 개발 세션 입력을 설계한다. 비교 가능한
   VALID 성공/실패만 목표 결과와 기준 장면 후보로 사용한다. 제외 이력·사유·기존 비용·
   미상 사용량은 별도 감사 목록에 남긴다. 운영자가 선택한 외부 이력임을 공개하고
   정식 AFS/Random arm에는 주입하지 않는다. 원본 suite나 남은 예산을 수정하지 않는다.
2. LLM 출력에 검증된 anchor case ID 선택을 추가한다. 허용 ID 안에서 기준 장면,
   지원되는 변경 축, 값 또는 범위, 가설, 근거, 실험 목적을 연결한다. 한 후보는 기준
   장면 대비 한 설정 축만 바꾸고, 실제 PASS/FAIL 양쪽 근거가 없으면 boundary라고
   부르지 않는다. 성공 측면 검사·다른 요인 대조·탐색·반복 확인은 구별한다.
3. 선택 감사와 결과 연결을 기존 보고서·failure memory에 붙인다. 무엇을 왜 골랐고,
   무엇이 중복·조건 불일치로 거절됐으며, 실행 후 무엇이 관측됐는지 추적한다.
   자유문 가설은 원인 판정이 아니다. 실제 실행 전 생성된 예상 결과를 발견 성과로 세지 않는다.

우선 사용 범위는 현재 goal-agent backend가 지원하는 17축이다. 장애물 위치·크기·
각도, 상자 배치·질량·마찰, 바닥 마찰, 통로 폭 등을 후보로 삼을 수 있다. 모든 축을
동시에 바꾸거나 무조건 더 어렵게 만드는 것이 목표가 아니다. 경사·계단·점프와
일반 랜덤 지형 backend까지 이미 통합됐다고 주장하지 않는다.

3.2m 중단 전 경로 거부와 중간 지점 접근은 보존할 관찰이지만 목표 실패 label로는
사용하지 않는다. 중단 trace를 추후 LLM 보조 입력에 넣으려면 관측 구간·중단 사유·
사용 불가 판단을 구분하는 별도 검증 계약이 필요하다. 첫 구현의 필수 입력으로 요구하지 않는다.

## 완료 기준과 이후 순서

첫 구현은 오프라인 실제 archive 및 합성 응답으로 검증한다. 기준점의 근거 ID와
조건 일치, 한 축 제약, 반대 결과 없는 경계 거부, 과거 조건 혼합 거부, 제외 비용
보존, 중복 억제, 원본 불변을 검사한다. 여러 기준점에서 다른 축을 고르는 합성 사례는
코드 연결 검증일 뿐 실제 LLM의 좋은 탐색 능력 증거가 아니다.

그다음에만 별도 예산 승인을 받아 Luna AFS 제안과 소수 로봇 실행을 점검한다.
검증된 실패는 기존 회귀 자산으로 편입하고, 방법·도메인·로봇 조건을 고정한 뒤
독립 seed의 공정한 AFS/Random 평가로 돌아간다. FDR 30%, 상대 Gain 20%, 6종 중
4종 coverage는 연구 목표이며 이번 성공 대조나 계획으로 달성된 것이 아니다.

이번 변경은 이 계획 이력, 색인, 현재 로드맵의 우선순위와 AGENTS 메모뿐이다.
write-page 스킬에 따라 기존 구현·제안·미검증 사항을 구분했다. 새 suite 생성,
API/GPU 실행, timeout/token/로봇 변경, 커밋·push는 하지 않았다.
