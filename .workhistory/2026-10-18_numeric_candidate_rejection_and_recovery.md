# 숫자 범위 위반 후보 분리와 저장 응답 복구

## 목표와 변경

사용자는 breadth 세션의 잘못된 후보 하나 때문에 정상 조합 후보까지 중단되는 문제를 수정하도록 요청했다. `breadth-v1`의 숫자 범위 오류만 후보 단위로 기록·제외하도록 바꾸고, 이미 저장된 응답을 재호출하지 않는 명시적 오프라인 복구 기능을 추가했다.

`llm_afs.behavior.validate`는 기본적으로 기존 전체 응답 검증을 유지한다. breadth 제안에서만 숫자 범위 거절 목록을 반환하는 명시적 경로를 사용한다. 첫 변경과 `extra_changes`의 두 번째 변경을 모두 검사하고, 잘못된 후보의 원래 값·범위·배열 인덱스를 기록한다. 원본 raw 응답, 값과 제안 순서를 바꾸지 않는다. 다른 유효 후보는 기존 배정·역할·근거·쿼터·중복 검사를 모두 통과해야 실행 후보가 된다.

`numeric_out_of_bounds` 외의 스키마/비유한 값/근거/컨텍스트/축/쿼터/역할 오류는 계속 전체 중단한다. 정상 대안이 없으면 `NoEligibleEndpoint`를 기록하고 기존 bounded-rejection 요청 상한 내에서 새 제안을 받는다. 숫자를 자르거나, 1m를 .8m로 보정하거나, 승인 범위를 늘리지 않는다. 옛 단일 축 모드는 기존 범위 오류 중단 계약을 유지한다.

## 이미 중단된 세션 복구

새 `tools/run_afs_autonomous.py recover-numeric`은 기본 dry-run, 명시적 `--apply`로 새 경로에 복구본을 만드는 오프라인 연산이다. 모델의 완료 응답과 모델명/사용량/원본 해시를 검증한다. 원본 요청과 재구성 요청은 새 숫자 거절 설명 부분만 차이가 날 수 있으며, 전체 입력·스키마·모델·다른 지침·설정은 같아야 한다. 기존 컨텍스트에 새로운 값을 재결합하지 않는다.

기존 시도는 유효하게 완료돼 있어야 하며 모호한 로봇 실행이나 유료 응답은 복구하지 않는다. 자원·런타임/관계없는 소스 드리프트, 기존 복구, 완료된 유효 목표 또는 시도 상한 도달도 거절한다. 허용 소스 변경은 숫자 검증/선택 연결, 설명, CLI 및 복구/감사 검증 파일로 한정한다. 코드 변경 사실은 새 소스 고정과 감사 이력에 공개한다.

복구본에는 원본 상태/프로토콜/ledger 사본과 해시, 전체 과거 제안·시도, 사용한 예산과 비용을 보존한다. 별도 `recovery.json`을 소스 고정에 결합하고 사본 변조도 재개 전에 차단한다. 원본 응답을 수정하지 않고 현재 선택기가 유효한 후보를 다시 선택한다. 저장된 후보는 로봇 실행 직전에 다시 검증한다. 운영자 보조 개발 연속 실행이지 독립적인 새 실험 성능 비교가 아니다. 과거 EpisodeRecord의 원본 경로는 그대로 필요하다.

## 검증

최종 관련 CPU 회귀 테스트 341개가 126.50초에 통과했다. 숫자 이상 후보의 앞/뒤 위치와 두 번째 축, 유효 대안 유지, 원본 불변, 다른 오류 중단, 모든 후보 거절 시 AFS 상한 차감과 로봇 미실행, 앞선 두 시도의 예산·비용 보존, 원본 해시 보존, 저장 조합의 무재호출 재개, unrelated/runtime 드리프트 거절, 원본 응답과 복구 감사 사본 변조 거절 및 기존 point/일반 복구 경로를 포함한다. 수정 Python 8개 파일의 Ruff 정적/포맷 검사도 통과했다.

초기 테스트 두 건은 구현 오류가 아니라 테스트 기대 문자열과 가짜 응답의 assistant role 누락을 수정한 후 통과했다. 실제 무료 dry-run에서 새 설명이 요청의 최종 suffix가 아닌 중간에 삽입돼 원본 요청 비교가 중단되는 문제를 발견했고, 새 설명을 최종 suffix로 옮겨 정확한 비교를 유지했다. 전체 요청 비교를 느슨하게 바꾸지 않았다.

실제 원본 `20261018T160156_325966Z`의 dry-run은 통과했다. 기존 시도 2회, AFS 3회가 유지되고 proposal_00002의 첫 후보(통로 폭 3.6m＋장애물1 Y 크기 .65m)가 선택됐다. 두 번째 후보의 장애물2 Y 크기 1m는 승인 범위 .2~.8m 위반으로 기록됐다. 유효 목표까지 10개, 시도 상한 안 14회, AFS 상한 안 17요청이 남는다.

무료 `--apply`로 실제 복구본 `/workspace/g1_failure/runtime/afs_autonomous/20261018T160156_325966Z_numeric_recovery`를 생성했다. READY/pending=null이며 위 조합이 선택돼 있다. 원본 세션 552개 파일의 경로·파일 해시 목록 집계가 생성 전후 동일했다(`863ffb026c16fe018e5d4dbe6cc8617bf6b1a6d91eec7b34f160243a0ced83f7`). 원본 상태 digest `e621ee9ac1ef270492693670730ccaa29de149629bb1ea88750035989e904b6f`, 원본 ledger 사본 SHA256 `91effaba02e05d0e4ce9205178ba2fb23b8666daf236518e345dac0b8daedefe`가 복구 감사에 결합됐다. 원본 응답 3개 파일도 그대로 유지했다.

복구본에 대해 `_fresh`의 소스·자원·근거 검증과 저장된 원본 응답의 `selected_probe` 재검증을 API 키 없는 읽기 전용 경로로 수행했다. 현재 컨텍스트에서 재구성한 후보가 저장 후보와 정확히 일치했다(`PRE_DISPATCH_REVALIDATION=MATCH`). 상태는 READY, 시도 2회, AFS 3회 그대로다. 이 점검은 실제 유료 run을 호출하지 않았다.

신규 유료/API/로봇/GPU 실행은 하지 않았다. 처음 무료 진단은 자동 안전 검토에서 API 실행 가능성 우려로 차단됐다. CLI와 호출 경로가 완료 JSON 추출·해시/이력 검증만 수행하고 dry-run에서는 디렉터리 생성 전에 반환함을 읽기 확인했다. API 키를 제거한 무료 명령으로 재검토를 받아 진단을 완료했다. 차단을 우회해 유료 호출을 수행하지 않았다.

## 문서와 인계

README, `scene2test/docs/AFS_BREADTH_SEARCH.md`를 갱신하고 `scene2test/docs/AFS_NUMERIC_RECOVERY.md`에 무료 dry-run, 복구 생성 및 이후 유료 재개 명령을 분리했다. 문서 작성 스킬에 따라 기존 중단 진단 기록은 덮어쓰지 않았다. OpenAI Docs의 [구조화 출력 지침](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)을 확인했으며, 요청과 호스트 검증의 책임을 분리했다. 새 축별 스키마 강제를 주장하지 않으며 서버 검증이 최종 범위를 보장한다.

유료 실험 결과나 실패 유형 발견 성과를 추가한 변경은 아니다. 기존 2FAIL의 라벨·판정·분모를 바꾸지 않았고 커밋/push도 하지 않았다.
