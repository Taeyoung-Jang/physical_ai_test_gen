# AFS 자동 탐색 중심의 후속 작업 계획

## 사용자 요청과 우선순위

사용자는 반복적인 수치 변경 시험과 매번 실행 명령을 넘기는 방식에 이의를 제기하고,
앞으로 어떤 개발이 필요한지 물었다. 다음 우선순위는 0.625 유료 시험 자체가 아니라,
**현재 행동 근거를 받아 여러 환경 축에서 다음 실험을 선택하고 정해진 예산까지 반복하는
개발용 AFS 실행 흐름**을 정비하는 것이다. 사용자가 매번 수치나 명령을 선택하지 않도록 한다.

이는 코드 확인에 기반한 후속 계획이다. 이 요청으로 구현이나 새 유료 캠페인이 승인됐다고
확대 해석하지 않았고, 이번에는 실행 코드·동결 실험·원본 판정을 변경하지 않았다.
기존 0.5 FAIL과 0.75 PASS는 유효한 근거로 유지한다. 앞서 제안한 0.5 반복/0.625 시험은
선택 가능한 국소 검증이며, 다음 개발을 시작하기 위한 필수 전제는 아니다.

## 확인한 현재 구현

자동 탐색 기능이 전혀 없었던 것은 아니다.

- `tools/run_afs_pilot.py`는 기존 AFS/Random campaign을 초기화·재개하고 유효한 실행을
  예산까지 자동 반복한 뒤 보고서를 만든다. 불완전/API 오류 결과에서는 자동 유료 재시도
  없이 중단한다.
- `research_campaign.py`는 자체 arm/seed의 이력으로 llm/boundary/exploration/repeat
  슬롯을 순환한다. 따라서 기존 정식 캠페인 전체가 항상 중간값만 고르는 것은 아니다.
- `behavior_feedback.py`에는 전체 행동 요약, SceneGraph, 로봇 조건, 실제 성공/실패,
  유사 실패 패턴, 성공 측면 탐색과 다른 가설 우선순위, 중복/cooldown 검증이 이미 있다.
- 최근 사용한 `afs_contrast.next_selection`은 혼합 결과 반복을 먼저, 그다음 관측 구간
  중간값을 고른다. 둘 다 없을 때만 LLM 요청으로 넘어간다. 이것이 최근 위치 축의 수치
  시험이 우선된 구체적인 코드상 이유다. 이 단일 축 개발 검증을 전체 AFS 목표로 취급하면 안 된다.
- 원본 무결성 검증, goal-only 판정, P1 failure memory, MP4, 회귀 실행기와 비용/지표
  보고 구성요소도 존재한다. 다음 작업은 이들을 다시 만드는 것이 아니라 재사용·연결하는 것이다.

참고 목표는 `.blueprint/Failure_Case_Goal.md`의 FDR 30% 이상, Random 대비 Gain 20%
이상, 사전 정의 여섯 유형 중 네 유형 이상 발견이다. 현재 결과가 이 목표들을 달성했다는
주장은 하지 않는다. `failure_taxonomy.py`의 등록된 operational 규칙은 여전히 충돌,
장애물 간섭, 목표 점유 세 종류이며, 규칙 수는 실제 발견 유형 수와 다르다.

## 바로 다음 개발 단위

### 검토된 이력을 사용하는 개발용 실행 세션

현재 같은 조건의 두 archive를 명시적 입력으로 받는 개발 세션을 설계한다.
직전 0.5 FAIL은 `20261003T150653_133405Z`, 0.75 PASS는
`20261003T154614_537450Z`다. 소스·자산·목표·예산·근거 무결성과 중복을 확인한다.
사람이 고른 외부 이력을 사용하는 개발용 탐색이라는 사실과 상속 비용을 표시한다.
이 이력을 옛 AFS/Random arm에 무료 초기 자료로 넣거나 동결 조건 검사를 우회하지 않는다.

### 한 축에 머무르지 않는 선택 정책

기존 LLM 가설·성공 측면 탐색·반복·관측 중간값 기능을 재사용하되, 개발 세션에서는
한 축의 중간값이나 같은 장면 반복이 새 가설을 계속 밀어내지 않도록 예산 배분과 전환 규칙을
명시한다. 반복/축별 사용량, 같은 행동 패턴 재관측, 새 정보 부족을 기록하고 다른 축이나
새 배치 가설로 넘어가는 이유를 남긴다. 세부 임계값은 구현 설계와 오프라인 검증에서 정한다.

첫 범위는 현재 로봇 backend가 실제로 지원하는 v4 18축이다. 위치, 통로 폭, 바닥·상자
마찰, 질량, 두 장애물의 위치·크기·높이·회전 등이 대상이다. 경사·점프·인식 오류처럼
별도 generator나 새 로봇 능력이 필요한 항목을 이미 지원되는 것처럼 제안하지 않는다.
로봇의 행동을 지시하거나 실패를 강제하는 명령은 AFS 출력에 넣지 않는다.

### 선택부터 실행과 분석까지 자동 반복

검증된 이력 → 가설/다음 장면 선택 → 장면 생성과 계약 검사 → 로봇 실행 → 목표 판정과
행동 근거·비용 수집 → memory 갱신 → 다음 선택을 하나의 지속 가능한 실행 흐름으로 연결한다.
기존 저장소 잠금·intent·재개·중복 방지·실행기를 재사용한다. 유효한 로봇 FAIL은 정상
탐색 자료로 처리하고, 인프라 오류·불명확한 유료 요청·손상 근거는 FAIL로 만들지 않는다.

처음 승인된 총 시도/로봇 호출/AFS 요청 예산 안에서 진행하고 재개해도 비용을 초기화하지
않는다. 수신되지 않은 사용량은 0이 아닌 unknown으로 남긴다. 현재 모델·출력 토큰 상한·
시뮬레이션 상한을 몰래 변경하거나 비용상한을 보장하지 않는다. 키가 없는 환경에서는
offline 검증까지만 가능하며, 사용자가 키를 넣은 한 프로세스에서 전체 흐름을 한 번
시작하도록 제공한다. 키를 파일/채팅에 넘기거나 타 프로세스에서 가져올 필요가 없게 한다.

### 사람이 읽을 결과와 회귀 자산 연결

왜 이 축/장면을 골랐는지, 실제 로봇이 어떻게 행동했는지, 어떤 가설이 아직 미확인인지,
새 정보 없이 반복한 비율과 비용을 기존 보고서·MP4·memory에 연결한다. LLM의 설명을
원인이나 공식 실패 유형으로 자동 확정하지 않는다. 유효 실패·성공 대조·반복 변동성을
보존하고 기존 회귀 suite로 가져갈 수 있도록 한다.

## 완료 판단과 검증 순서

먼저 저장된 실제 archive를 입력으로 한 오프라인 통합 검사와 합성 결과 시퀀스로 검증한다.
다음 항목을 통과한 뒤 새로 승인된 소규모 live 예산으로 연결을 확인한다.

- 실행을 한 번 시작하면 유효한 PASS/FAIL마다 사용자에게 새 명령을 요구하지 않는다.
- 실제 행동 근거가 다음 선택에 들어가고, 한 축/같은 패턴 반복에서 벗어나는 규칙이 작동한다.
- 중단/재개가 이미 보낸 유료 호출을 복제하거나 전체 예산을 리셋하지 않는다.
- 과거 자료와 새 비용, 개발 탐색과 정식 비교, goal 실패와 인프라 오류를 구분한다.
- 원본·robot condition·판정 기준을 보존하며, 단순 mock 검사를 live 성공으로 보고하지 않는다.

## 그다음 전체 로드맵

자동 개발 탐색을 확인한 뒤 장면·관측·분류기 범위를 함께 확장한다. 특히 네 번째 실패 유형은
이름만 추가할 수 없고 실제 scene, 관측 계약, 검증된 분류 근거가 필요하다. 별도 사람 근접
계약/계산기 등을 재사용할 수 있으나 live trace 연결은 남은 일이다. 안전 노출 자체를
원래 goal FAIL로 바꾸지 않는다. 현재 GT 지도 조건에서 인식 오류 검증도 별도 설계가 필요하다.

마지막으로 탐색 정책과 로봇 조건을 고정한 새 독립 AFS/Random 비교에서 동일 예산과 여러
seed로 FDR/Gain/지원되는 diversity를 계산한다. 개발에 사용한 이력을 평가 arm에
끼워 넣지 않고 실패율이 높은 것만으로 다양성이나 우월성을 주장하지 않는다.

## 이번 작업의 산출물

실행 코드와 목표 문서를 읽고 이 계획, 이력 index, workspace memory를 갱신했다.
write-page 스킬을 사용해 기존 구현, 새 제안, 후속 검증을 구분했다. 새 API·GPU·로봇 실행,
suite/DB 생성, 코드 수정, commit/push는 하지 않았다. 무제한 자동 실행을 약속하거나
이 계획 정리를 별도 유료 실행 승인으로 간주하지 않는다.
