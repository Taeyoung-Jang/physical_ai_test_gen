# 자동 AFS 첫 실제 실행 결과와 후속 개선 검토

## 결론과 검토 범위

사용자가 실행한 첫 자동 개발 AFS는 정해진 6회 시도를 완료했다. 5회 PASS, 1회 FAIL,
제외 0회, pending 없음이며 AFS 5회와 로봇 52회 호출을 사용했다. 실패를 관측한 뒤
완화 배치와 관측 구간 중간값을 검사하고 다른 장애물 축으로 전환한 흐름을 확인했다.
이는 실제 자동화 연결의 검증이지 AFS/Random 우월성, 확정 실패 경계 또는 새 유형 발견의
검증은 아니다. 유일한 실패는 목표 영역 진입 후 요구 체류 시간을 못 채운 예산 종료였다.

검토 세션은 `/workspace/g1_failure/runtime/afs_autonomous/20261003T165928_663622Z`이며,
보고서는 `reports/20261003T173419_661417Z/report.html`이다.
이번 검토에서는 추가 API·로봇·GPU 실험, 소스 코드 수정, 원본/DB/판정 변경,
기존 suite 재개, 커밋·push를 하지 않았다. 작업 기록과 workspace memory만 갱신했다.

## 원본과 선택 흐름 검증

SQLite를 `mode=ro`로 읽어 snapshot digest, lock, 보고서의 attempts/proposals와 일치함을
확인했다. 새 rollout 6개의 artifact hash는 각각 65, 77, 49, 70, 73, 74개로 총 408개가
일치했다. 이전 FAIL/PASS의 71개/56개도 다시 검증했다. 보고서 manifest 316개 및
AFS request/context/response 5세트의 저장 해시도 모두 일치했다.

6회 모두 기존 검토 기록과 같은 normalized condition
`eb42efe331685d6e51813b38195d27a88f50b1da77b25bd15cd9c296b42b95aa`다.
후보 파라미터와 실제 rollout scene_config도 일치했다. Robot/goal/예산의 변경을
scene 변화로 잘못 계산한 것은 아니다.

저장 응답과 단계별 실제 이력으로 context·요청 의미·후보 선택을 무료 재계산했다.
5개 context digest, 의미상 request 내용과 endpoint 선택, 1개 local midpoint 모두 일치했다.
상세 이력의 episode 수는 2, 3, 4, 4/전체6, 4/전체7로 증가했다. 단순 고정 scene
목록 실행이 아니라 새 행동 근거가 후속 제안에 들어간 것이다.
다만 요청 JSON 문자열의 key-order 비교에는 아래 별도 재개 취약점이 확인됐다.

## 여섯 번의 선택과 실제 결과

변경 전 값은 직전 실행이 아니라 **각 후보에 기록된 anchor**의 값이다. 특히 4번은
직전 3번의 배치를 그대로 수정한 것이 아니라 1번 PASS를 anchor로 한 X 중간값 검사다.

| 순서와 attempt | 변경한 축 | anchor에서 시험값으로 | 결과 | 로봇 호출 | 최종 목표 거리 |
|---|---|---|---|---:|---:|
| 1 / 00000 | 상자 측면 비율 | 0.75 → 0.625, X 7.0m | PASS | 8 | 0.231441m |
| 2 / 00001 | 상자 X | 7.0 → 7.5m, 측면 비율 0.625 | FAIL | 10 | 0.241504m |
| 3 / 00002 | 상자 측면 비율 | 0.625 → 0.9, X 7.5m | PASS | 5 | 0.114662m |
| 4 / 00003 | 상자 X | 7.0 → 7.25m, 측면 비율 0.625 | PASS | 10 | 0.224957m |
| 5 / 00004 | 두 번째 고정 장애물 측면 비율 | −0.7 → −1.0 | PASS | 10 | 0.199089m |
| 6 / 00005 | 첫 번째 고정 장애물 로컬 Y 크기 | 0.5 → 0.2m | PASS | 9 | 0.230291m |

첫 0.625는 host가 강제한 midpoint가 아니라 LLM이 0.625~0.675 범위를 제안해 선택된
끝점이다. 4번만 기존 관측 PASS X7.0 / FAIL X7.5의 local midpoint로, 추가 AFS 요청이 없다.
18축 중 4축을 실제 바꾸었고, 상자 X/측면 비율 각각 2회, 나머지 2축 각각 1회다.
직전 변경 축 제외와 축별 한도가 적용됐다. 명시적 같은 장면 반복은 0회다.

새 실행만으로 X 7.25 PASS~7.5 FAIL(측면 비율 0.625), 측면 비율 0.625 FAIL~0.9 PASS
(X7.5)의 관측 구간이 생겼다. 이전 근거 포함 시 X7.0의 측면 비율 0.5 FAIL~0.625 PASS도
포함되어 총 3개다. 단회 관측이며 단조성·인과성·재현 성공률을 확정하지 않는다.

## 유일한 FAIL의 실제 행동

attempt_00001은 `VALID/FAIL/BUDGET_EXHAUSTED`, 시뮬레이션 255.065초다.
실행된 행동 10개는 plan_path 1개, navigate_to 7개, 직접 속도 move 2개다.

1. 목표 중심 (7,0) 경로 조회가 `blocked_endpoint`를 반환했다.
2. GPT는 (6.95,−0.2) 중간 목표를 세 번 따라간 후 목표 중심을 재요청했지만 다시 막혔다.
3. (6.58,0.875), (6.8,−0.1), (6.9,−0.22)로 중간 목표를 변경했다.
4. 마지막 두 호출은 몸체 좌표 속도 (0.06,0.13,0)로 0.6초와 0.65초 이동을 요청했다.
   최종적으로 반경 0.25m 안의 0.241504m까지 들어갔지만 체류는 0.27초였다.
5. 계약의 1초에서 0.73초가 부족한 상태로 호출 10회를 소진했다. 마지막 직접 이동은
   목표 자동 hold 명령이 아니며, 마지막 navigate_to도 중간 목표였다.

마지막 plan_summary는 다음 최종 호출로 navigate/hold하겠다고 설명했지만 그것이 이미
10번째 호출이었다. 이는 기록상 마지막 행동 계획과 남은 예산이 맞지 않은 관측이다.
API 장애나 물리적 통과 불가능의 증거는 아니다. 시간을 더 주면 반드시 성공한다는
반사실적 결론도 내리지 않고, goal 계약·예산·판정을 그대로 보존한다.

6개 실행 모두 밀기 동작, 기록된 넘어짐, 바닥 이외 robot/world 접촉이 없었다.
유일한 FAIL의 상자 XY 이동은 약 1.86e−8m로 실질적 이동이 없다.
따라서 무거운 상자 밀기 실패나 균형 상실로 해석하면 안 된다. 분류 근거가 없는
새 failure family를 붙이지 않는다.

PASS는 모두 최종 계약의 1초 goal-region dwell을 만족했다. 샘플링된 states의 최댓값이
0.97~0.99초로 보이는 경우도 있으나 최종 result/tool 상태와 샘플 주기의 차이다.
1, 4, 5, 6번은 호출 수보다 실행 행동이 하나씩 적다. 목표가 추론 대기 중 완료되어
그 후 도착한 응답을 실행하지 않았고, 이 네 호출의 비용도 보존했다. 총 52호출/48행동이다.

## AFS 가설의 품질과 남은 측정 개선

이번에는 실패한 X7.5 배치를 유지한 채 측면 비율을 0.9로 완화해 PASS를 관측했다.
이는 사용자가 원한 실패 유지·증폭 대신 성공 측면을 확인하는 탐색에 부합한다.
이후 다른 장애물 축으로 넘어가기도 했다. 다만 후반 두 제안은 장애물을 더 옆에 두거나
작게 만드는 방향이었고, 이미 PASS인 anchor에서 다시 PASS가 나왔다. 이 좁은 예산에서
더 많은 실패나 새로운 실패 행동을 찾는 데 얼마나 기여했는지는 아직 입증되지 않았다.
다음 선택 정책은 성공 기준선에서 의미 있는 도전 가설, 실패 완화, 국소 확인을 균형 있게
배분하고 이미 충분한 성공 측면만 계속 확인하지 않는 방향을 검토할 가치가 있다.

기하 근거도 개선할 수 있다. XML의 상자 반크기는 X0.4/Y0.55m였다. 새 여섯 장면의
초기 상자 투영은 모두 goal disk와 겹치지 않았다. goal 중심에서 box AABB까지 거리는
1번 0.325m, FAIL 2번 0.340037m, 3번 0.717008m, 4~6번 0.325m다.
0.25m goal disk의 점유와 0.40m 이상 여유를 요구하는 로봇 계획기의 endpoint 제한은 다르다.
LLM 가설의 “목표 겹침 감소” 표현은 이미 겹침이 0인 경우 설명력이 약하다. 후속 요청에
실제 투영 겹침, 계획기 여유와 최종 체류·호출 잔여량을 명확히 구분해 제공하는 것이 적절하다.
이는 새로운 원인 판정이나 로봇 행동 지시를 추가하자는 뜻이 아니다.

## 재개 경로에서 발견한 별도 취약점

현재 완료 세션은 재개가 필요 없고 6회 결과가 손상된 것도 아니다. 하지만 저장된 실제
자료를 DB에서 읽어 context를 재구성하면 proposal_00001 이후 네 요청에서 context hash와
요청 의미는 같아도 `input[0].content`의 JSON 문자열 key order가 달라졌다.
안쪽 JSON을 parse한 뒤 비교하면 모두 같고 후보 선택도 모두 일치했다.

`afs_autonomous.py`의 `_finish_proposal`은 현재 전체 request dict를 그대로 비교한다.
따라서 **응답 저장 후 검증 완료 전 중단**되어 DB에서 복원하는 경우 같은 내용을
`saved proposal request changed`로 오인할 수 있다. SQLite snapshot은 sort_keys로
저장되고, request의 안쪽 content는 JSON 문자열이어서 바깥 dict 비교만으로 정규화되지 않는다.
처음 오프라인 재계산에서 이 비교 실패를 발견했고, 의미와 선택의 재검산으로 범위를 좁혔다.

다음 코드 수정의 우선 후보는 엄격한 content JSON 정규화/의미 비교와 실제 순서 차이를
포함한 중단 재개 회귀 테스트다. context/schema/model/instructions 검사를 약화하거나
불명확한 유료 요청을 재전송하면 안 된다. 이번 검토에서는 수정하거나 pending 상태를
인위적으로 만들지 않았고, 완료 세션의 DB도 쓰지 않았다.

## 비용과 영상

새 로봇: 52호출, 입력 1,576,963 / 출력 158,893 tokens. 새 AFS: 5호출, 입력 213,425 /
출력 8,092 tokens. 합계 새 입력 1,790,388 / 출력 166,985이며 수신 usage 누락은 없다.
과거 두 로봇 기록의 16호출, 입력 473,907 / 출력 142,066은 별도다. 과거 AFS 선택 비용은
robot archive에 없어 unknown이며 청구액은 이 기록만으로 산정하지 않았다.

4번 rollout의 두 응답은 약 253.65초/198.22초, 출력 48,845/37,959 tokens였다.
두 응답의 86,804 tokens는 새 로봇 출력 전체의 약 54.63%다. HTTP200이고 재시도는 없었다.
긴 응답을 timeout이나 보행 악화로 해석하지 않는다. 사용자 요청대로 토큰 상한을 다시
도입하거나 모델·추론 설정을 몰래 바꾸지 않았다. 비용·지연 편차는 계속 관측할 항목이다.

MP4 6개를 ffmpeg 전체 디코딩 검사해 모두 성공했다. GIF는 0개다. 실패의 마지막 호출 전
camera_009.png도 확인했지만 이 정지 영상만으로 지각 오류나 물리 실패를 판정하지 않았다.

## 다음 판단

자동 실행 연결은 실제 데이터로 정상 동작했다. 다만 단회 실패와 단회 성공 구간을 얻은
개발 세션이므로 정식 FDR/Gain/다양성 목표 달성을 주장하지 않는다. 전체 예산을 다 사용해
같은 세션을 계속 돌릴 필요는 없다. 우선 재개 비교 취약점과 AFS 가설·도전/완화 배분을
보완하는 것이 적절하다. 수동 숫자 실험을 사용자에게 다시 연속 요청하거나 로봇 기능
개발로 우선순위를 옮기지 않는다.

write-page 지침에 따라 관측, 원인 가설, 잠재 코드 문제, 아직 실행하지 않은 개선안을
구분해 기록했다. 추가 유료 실행이나 코드 변경은 이번 결과 검토에 포함되지 않는다.
