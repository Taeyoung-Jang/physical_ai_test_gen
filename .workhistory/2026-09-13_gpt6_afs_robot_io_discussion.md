# GPT-6의 AFS/로봇 적용 및 입출력 설계 후속 논의

작성일: 2026-09-13 UTC.
범위: AFS LLM-first 문서 저장 이후 사용자와 나눈 대화 기록.
성격: 결정·선호·제안·미확정 사항을 구분한 요약. 구현 완료 명세가 아니다.

이전 기록:
- [AFS LLM-first 설계](../scene2test/docs/AFS_LLM_FIRST_DESIGN.md)

## 1. 사용자가 명시한 방향

1. GPT-6를 AFS 쪽과 로봇 쪽 양쪽에 도입하고 싶다고 밝혔다.
2. 우선순위는 **AFS 먼저**다. 로봇 VLM 연결을 AFS 착수의 선행 조건으로 두지 않는다.
3. AFS 출력은 새로운 **failure scene space**이며, 이를 바탕으로 실제 scene을 생성할
   수 있기를 원한다. 단일 후보의 결과 예측만을 원하는 것은 아니다.
4. AFS 입력으로 기존 scene space, robot spec, task goal을 제시했다.
5. 이후 제안한 입력 확장과 후보 탐색 공간 출력 방향에 긍정적으로 응답했다.
6. 로봇용 GPT-6가 카메라를 보고 행동하는 향후 구성을 고려해 설계하기를 요청했다.
7. 최신 추가 의견: 로봇에 **전체 지도와 GPT-6를 함께 제공하는 구성도 가능**하다고
   제안했다. 이미 알려진 지도에서 이미지 등으로 현재 위치를 추정하는 localization을
   활용할 수 있다는 취지다. 이를 번외 아이디어로 언급하고 대화 기록을 요청했다.

이번 요청은 이력을 남기는 것이며, 새로운 API 호출·기능 구현·실험 실행은 하지 않는다.

## 2. GPT-6의 두 역할

| 역할 | 입력 | 출력/목적 |
|---|---|---|
| AFS 모델 | 장면 공간, 시험 대상 설정, 태스크, 과거 관측 | 시험할 환경 영역·조건 제안 또는 후보 결과 예측 |
| 로봇 상위 모델 | 영상, 목표, 허용된 지도·상태·관측 이력 | 하위 목표, 이동/정지/재계획 요청 |
| GR00T 보행 정책 | 속도 명령과 고유수용 상태 | 관절 목표를 만드는 하위 행동 |
| 독립 평가기 | 실제 실행 상태·궤적·접촉·시간 | 고정된 성공/실패/유효성 판정 |

로봇이 영상과 언어 목표를 함께 사용하면 GPT-6의 시각 기능을 사용하는 VLM 기반 상위
정책이라고 설명했다. 로봇용 모델을 추가한다고 해서 관절 토크 직접 출력이나 발걸음 계획까지
자동으로 구현되는 것은 아니다. VLM과 로봇 행동 출력에 맞춰 학습된 VLA를 구분한다.

앞선 답변에서 공식 문서를 확인하고 GPT-6 Astra (`gpt-6-astra`)의 텍스트·이미지 입력,
구조화 출력·함수 호출 지원을 소개했다. 직접 비디오 입력 대신 이미지 프레임 전달을 설명했다.
이는 API 기능 확인이지 사용자 계정의 접근 권한 확인이나 G1 제어 효과 검증은 아니다.
사용자는 GPT-6 사용을 원하지만 구체 snapshot, reasoning 설정, 비용/지연 한도는 미정이다.

참고했던 공식 문서: https://developers.openai.com/api/docs/models/gpt-6-astra
이번 기록 작업에서는 외부 문서를 다시 조회하지 않았다.

## 3. 현재 GR00T 입출력에 관해 확인한 설명

`scene2test/src/simulation_server/groot_locomotion.py`와 G1 YAML/XML을 확인해 설명했다.
대상은 GR00T 제품군 전체가 아니라 현재 연결한 `GR00T-WholeBodyControl-Walk.onnx`다.

한 시점 입력 86차원:

| 입력 | 차원 |
|---|---:|
| 전후·좌우·회전 속도 명령 | 3 |
| 목표 몸체 높이 | 1 |
| 목표 roll/pitch/yaw | 3 |
| 몸체 각속도 | 3 |
| 몸체 좌표계의 중력 방향 | 3 |
| 기준 자세 대비 관절 각도 | 29 |
| 관절 속도 | 29 |
| 이전 정책 출력 | 15 |

최근 6개 관측을 연결해 516차원을 입력한다. 영상, SceneGraph, 전역 목표 위치, 높이 지도는
이 보행 정책에 직접 입력되지 않는다. 현재 몸 상태는 MuJoCo에서 읽는다.

출력은 15개 값: 양 다리 12개 관절과 허리 3개 관절.
`target = default_angles + 0.25 * action`으로 목표 각도로 변환하고 PD 제어로 토크를
계산한다. 29개 구동 관절 전체를 모델이 직접 출력하는 것이 아니다. 나머지 팔/손목 14개는
현재 어댑터의 별도 PD 제어로 영점 자세를 유지한다.

최근 설정의 물리 timestep 0.005초, decimation 4에서 물리/PD는 시뮬레이션 시간 기준
200 Hz, 정책 추론은 50 Hz다. 실제 벽시계 처리 속도나 API 응답 주파수를 뜻하지 않는다.
기존 navigation follower가 정답 지도·위치를 이용해 주로 전진/회전 명령을 만든다.
이 사실로 향후 VLM 지도 기반 localization이 이미 구현됐다고 해석하면 안 된다.

## 4. AFS 입력 계약 제안

사용자의 세 가지 입력에 정책·관측 조건, 변경 제약, 실험 이력을 추가하는 안을 논의했다.

1. **기준 Scene Space:** SceneGraph, SceneSpec/기하, 객체 관계·표면 속성, 기존 도메인.
2. **Robot Spec:** 크기, 관절, 충돌 형상, 구동 제한. 미검증 능력 한계를 확정값으로 넣지 않음.
3. **Task Goal/Spec:** 목표, 출발 조건, 성공/실패 기준, 시간 제한.
4. **Policy / Observation Spec:** 정책, 센서, 지도·위치 정보 사용 조건, 행동 인터페이스.
5. **변경 제약/생성기 기능:** 지원되는 요소와 속성, 허용 범위, 고정 요소, 기하 유효성 규칙.
6. **실험 이력/예산:** 실제 실행 조건·결과·지표, 생성 무효/실행 오류, 남은 예산.

같은 하드웨어라도 정책·관측이 다르면 실패 조건이 달라질 수 있으므로 robot spec만으로
시험 대상을 정의하지 않는다. 초기 실험 이력은 비어 있을 수 있으며 실제 관측만 누적한다.

## 5. 출력 계약: 후보 failure scene space

사용자 요구에 따라 첫 접근은 순수 surrogate보다 **실패 탐색 공간 제안기**에 가깝다.
이전 결과를 반영하여 다음 영역을 제안해야 적응형 AFS가 된다. 결과 예측과 후보 생성 역할을
혼동하지 않고 실험 방법의 명칭과 비교 범위를 명확히 해야 한다.

제안한 출력 구성:

- 기준 scene revision 및 proposal/space ID.
- 변경 대상의 명시적인 파라미터 경로와 탐색 범위.
- 고정할 로봇·정책·목표·환경 요소.
- 검증할 실패 가설(관측 사실이나 확정된 원인이 아님).
- 바로 실행할 수 있는 구체적인 대표 후보 파라미터 조합.
- 생성기가 해석할 수 있는 제한된 구조화 JSON. 임의 실행 코드/XML을 직접 생성하지 않음.

설명용으로 `failure-space-proposal-v1`, 경사각 2–8도/마찰 0.15–0.6 및 대표 후보를
예시로 들었다. 이 이름과 수치들은 최종 schema나 검증된 실패 영역으로 확정한 것이 아니다.
각 파라미터 경로는 실제 기준 장면/생성기에서 지원해야 한다.

실행 전에는 ‘failure space’라도 **실패가 의심되는 후보 공간**이다. 생성/실행/평가 전에
실패 영역으로 확정하거나 예측을 실제 학습 관측에 넣지 않는다.

```text
GPT-6 후보 공간 제안
  → schema/범위/고정 조건 검사
  → 대표 후보 또는 Random/Sobol로 구체적 시험점 선택
  → SceneSpec 및 SceneGraph/지도/XML 공동 생성·검증
  → 로봇 실행·독립 평가
  → 관측 이력 갱신 → 다음 제안
```

따라서 LLM이 영역을 제안하고 Sobol이 내부를 샘플링하는 조합도 가능하다. 이것을 순수
LLM surrogate 교체 실험과 동일하게 부르지 않는다.

LLM은 성공 기준·시간 제한·로봇 정책을 임의로 변경할 수 없다. 지원하지 않는 장면 요소나
무효 장면을 실패로 인정하지 않는다. 첫 구현에서 고정 장면 구성의 수치 파라미터부터
제안하도록 하자는 안을 제시했으며, 장면 구조 변경의 구체 범위는 아직 미정이다.

통로를 완전히 막는 목표 불가능 장면의 허용 여부는 별도 실험 계약이다. 첫 구현에서는
기존 경로 존재 조건 유지안을 제시했다. 불가능한 목표를 인지하고 중단하는 능력을 평가하는
실험과 이동 가능한 환경에서의 실패 탐색을 섞지 않는다.

## 6. 향후 로봇 VLM을 위한 교체 가능한 시험 대상

다음 항목을 분리해 관리하는 설계를 제안했다.

- robot_spec: 하드웨어/충돌 모델.
- observation_spec: 실제 제공되는 카메라·지도·위치/상태 정보.
- policy_spec: 모델/프롬프트/도구, 상위 판단 역할.
- action_interface: 하위 목표·제한된 행동과 실제 제어 명령의 연결.
- low_level_controller: GR00T 정책과 PD 제어.
- task_spec: 목표와 평가 계약.

한 AFS 비교 중 이 시험 대상은 고정한다. 환경 탐색과 정책 개선을 동시에 수행한 결과를
하나의 고정 정책에 대한 실패 발견 효과로 해석하지 않는다.

로봇용 기록으로 실제 전달한 영상·관측, 상위 모델 출력, 하위 목표, 실제 제어 명령,
호출 지연/실패 처리, 궤적·접촉을 남기자는 안을 제시했다. 이는 원인 분석의 근거이지
LLM 설명을 자동으로 정답 원인 분류로 사용하는 설계가 아니다.

물리 조건 외 조명·그림자·대비·가림·유사 표지 등을 향후 시각 조건으로 제안할 수 있다.
현재 모두 구현된 기능이 아니므로 생성기의 capability 목록으로 지원 여부를 제한해야 한다.

## 7. 최신 사용자 의견: 전체 지도 + 카메라 localization + GPT-6

사용자는 로봇에 전체 지도를 주면서 GPT-6와 카메라 기반 위치 추정을 함께 활용하는 구성을
제안했다. 이 아이디어는 **배제하지 않으며**, ‘로봇 VLM은 지도 없이 센서만 받아야 한다’는
제약으로 설계하지 않는다. 이전 답변의 센서-only 구성은 하나의 실험 조건이지 필수 조건이 아니다.

개념상 다음 정보를 분리해서 계약에 기록할 수 있다(아래는 정리 제안, 구현/최종 합의 아님).

| 구분 | 정의해야 할 내용 |
|---|---|
| 지도 | 전체/부분, 사전 제공/온라인 생성, 2D/3D/semantic 표현, 현재 환경 revision과 일치 여부 |
| 위치 | 시뮬레이터 정답 pose인지, 센서로 추정한 pose인지, 초기 위치를 제공하는지 |
| localization | 별도 알고리즘 사용 여부, 입력 센서, 실패/불확실성 처리 |
| GPT-6 | 지도·영상·추정 pose 중 무엇을 받아 어떤 상위 판단을 하는지 |
| 경로/보행 | 경로 계획·추종·안전 검사·GR00T가 담당하는 범위 |

알려진 지도에서의 localization과 지도 작성까지 포함하는 SLAM은 구현 범위를 구분한다.
GPT-6 자체가 정밀 localization이나 SLAM을 수행한다고 가정하지 않는다. 사용자의 요지는
그런 기존 알고리즘을 함께 활용할 수 있다는 것이며, 특정 알고리즘·센서·지도 형식은 미정이다.

AFS와 로봇이 같은 환경 지도를 받는 것은 **명시적으로 허용된 실험 조건이면 가능**하다.
분리해야 할 것은 비공개 실패 가설·예상 정답·향후 rollout 결과 등이 로봇의 문맥으로
의도치 않게 새어 들어가는 것이다. 전체 지도 제공과 정답 pose 제공은 같은 조건이 아니다.
‘전체 지도 + 추정 위치’와 ‘전체 지도 + 정답 위치’를 별도 설정으로 기록해야 한다.

예시적인 향후 구성:

```text
사전 지도 + 카메라/허용 센서 → localization → 추정 pose
지도 + 영상 + 추정 pose + 언어 목표 → GPT-6 상위 판단
상위 목표 → 경로/실행 계층 → GR00T 보행 → 시뮬레이터
```

단, 모듈 연결 순서와 API, 카메라 설정, depth/IMU 사용 여부, 지도 업데이트 정책은 아직
정하지 않았다. 이번 기록을 해당 모듈 구현이나 실험 실행 승인으로 해석하지 않는다.

## 8. 다음 작업의 범위와 이번 기록 작업

우선 AFS용 GPT-6의 작은 입력/출력 계약과 실행 연결을 구체화한다. 로봇 측 map-assisted
VLM/localization은 observation/policy 계약에서 수용 가능하게 설계하되, 즉시 구현할 필수
선행 과제로 확대하지 않는다. AFS 코드 구현, API 인증, 호출 비용, 첫 실험 범위는 별도 확정한다.

이번 작업 시작 시 git status --short는 깨끗했다. 기존 문서/코드/실험 결과는 수정하지 않고
이 파일만 추가했다. 유료 API 호출, GPU 실행, 서버 변경, Git commit/push는 하지 않았다.
