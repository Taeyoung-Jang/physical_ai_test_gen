## 이번 사용량과 누적 사용량

| 항목 | 이번 3.6m 실행만 | suite 신규 실행 누적 2회 |
|---|---:|---:|
| 로봇 API 호출 | 6 | 13 |
| 입력 토큰 | 150193 | 354867 |
| 출력 토큰 | 2121 | 43356 |

사용자 로그의 new_execution_costs는 첫 4.0m 실행과 이번 실행의 누적이다. 따라서
출력 43356개가 이번 한 번에 발생한 것은 아니다. 이번 개별 응답은 약 3.54–9.27초였고
직전 실행의 164.68초·출력 39230개짜리 응답은 반복되지 않았다. 원인이 해결됐거나
향후 비용이 일정하다고 주장할 수는 없다. 토큰 수는 관측 사용량이며 청구액은 아니다.

도구 실행시간 합계는 44.700초, API wall latency 합계는 약 33.021초다. 시뮬레이션
전체 시간과 API wall 시간은 다른 척도이며 단순히 더해 정확히 일치해야 하는 값은 아니다.
모델이나 토큰 기본값을 바꾸지 않았다. AFS 선택 API 비용은 여전히 빈 목록이고,
기존 성공 두 번의 비용은 inherited_history_costs에 따로 보존돼 있다.

## AFS 의미와 다음 실행

저장된 memory에는 장면 사례가 2개다. 4.0m는 기존 두 번과 이번 suite 기준선 한 번을
합쳐 PASS 3/FAIL 0, 3.6m는 PASS 1/FAIL 0이다. 두 장면을 동일 장면 4회 성공으로
합치지 않는다. duplicates 0, exclusions 0, observed brackets 0이다.

3.6m 성공은 탐색 실패가 아니다. 성공 쪽 표본을 확보했으므로 이후 더 좁은 장면의
FAIL과 비교할 근거가 생겼다. 하지만 지금은 두 폭에서 성공했다는 관찰뿐이며,
그 사이 모든 폭이 성공하거나 3.2m에서 실패한다는 단조성·경계 주장은 불가능하다.
폭을 바꾸면 fraction 기반 장애물 Y좌표도 파생 변경될 수 있어 순수 벽 간격만의
인과효과로 해석하지 않는다. 운영자가 선택한 개발 대조이며 AFS/Random Gain 근거도 아니다.

READY/pending=null은 `--max-new-attempts 1`로 두 번째 시도만 마친 정상 상태다.
다음 명령을 같은 실행 디렉터리에서 한 번 더 실행하면 남은 3.2m 시도를 수행한다.

```bash
cd /workspace/g1_failure/src/physical_ai_test_gen/scene2test
uv run --no-sync python tools/run_afs_contrast.py run --suite /workspace/g1_failure/runtime/afs_contrast/navigation_v3_width_20261002 --live --max-new-attempts 1
```

3.2m까지 확인한 뒤 같은 축의 성공/실패 구간이 관측되면 중간값 검사를 준비하고,
모두 성공하면 다음 축·값의 근거 기반 선택을 검토한다. 아직 후속 배치를 생성하거나
LLM/로봇을 추가 호출하지 않았다. 원래 3회 예산을 늘리거나 옛 비교 캠페인을 재개하지 않는다.
