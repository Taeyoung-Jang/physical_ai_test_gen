# LLM 기반 AFS 탐색 방법 — 구현 기준 설명

기준일: 2026-09-15. 대상: `llm_afs/expanded.py`와 `tools/run_expanded_afs.py`의 v2.
이 문서는 현재 코드의 작동 방식과 연구상 해석을 설명한다. 새 API 호출이나
GPU 실험을 수행한 결과 보고서가 아니다. 실행 안내는 [확장 AFS 문서](EXPANDED_LLM_AFS.md) 참조.

## 1. 무엇을 하려는 방법인가?

AFS(Active Failure Search)의 목적은 제한된 실험 예산으로 로봇 시스템이 실패하는
환경 조건을 찾아내는 것이다. 로봇을 학습시키거나 보행 정책을 수정하는 작업과는 다르다.

현재 방법은 **LLM이 실패 가능성이 있는 환경의 부분 공간을 제안하고, 프로그램이
그 안팎에서 장면을 생성하여 실제 시뮬레이션으로 확인하는 혼합 탐색**이다.

LLM은 다음 역할을 하지 않는다.

- 로봇 관절 명령 생성 또는 로봇 카메라 기반 행동 결정.
- 실제 실행을 대신한 성공/실패 판정.
- 학습된 수치 대리 모델처럼 보정된 실패 확률이나 불확실성 출력.
- 사용자 허용 범위를 벗어난 임의의 코드·XML·새 장애물 종류 생성.

따라서 현재 구현을 부를 때는 “LLM-guided scene-space search” 또는
“LLM 기반 환경 부분 공간 제안 + 혼합 탐색”이 정확하다.

## 2. 전체 처리 과정

```text
사용자 설정: 허용 코스·환경 범위 + 로봇·정책·관측·목표
                         ↓
기준 SceneGraph + 검증된 이전 실행 결과 → LLM에 전달
                         ↓
LLM: 탐색할 코스와 조건 범위, 실패 가설을 구조화해서 제안
                         ↓
호스트: 제안의 타입·경로·범위·설정 식별자 검사
                         ↓
전체 범위 / LLM 제안 범위 / 관측된 실패 주변에서 수치 추출
                         ↓
SceneSpec → SceneGraph·이동 지도·MuJoCo XML·미리보기 생성 및 검증
                         ↓
유효한 장면만 별도 GPU runner로 로봇 실행 → 실행 유효성·목표 성공 평가
                         ↓
결과/자원/코드/산출물 검증 → 다음 라운드의 관측 이력으로 전달
```

현재 이 전체 과정이 하나의 무인 반복 명령으로 묶여 있지는 않다.
제안/생성, GPU 실행, 결과를 가져오는 다음 라운드는 별도 명령이다.

## 3. LLM 입력

| 입력 | 실제 제공 내용과 의미 |
| --- | --- |
| 기존 scene space | 승인된 코스 레시피와 각 파라미터의 타입·최솟값·최댓값·선택지 |
| SceneGraph | 각 승인 코스의 기준 설정에서 생성한 구조화된 그래프와 revision |
| Robot Spec | 현재 설정에 적힌 로봇 식별자·충돌 모델 등; 완전한 물리 모델 자동 요약은 아님 |
| Policy Spec | 실행 정책 식별자와 상위 제어 조건; 현재 로봇 VLM은 꺼져 있음 |
| Observation Spec | 현재는 전체 ground-truth 지도와 시뮬레이터의 실제 위치 사용, 카메라 정책 입력 없음 |
| Task Spec | 도착 목표 의미, 성공 기준 설명, 속도, 최대 시간, 물리 시간 간격, 초기 안정화 시간 |
| 실행 이력 | 검증된 결과의 파라미터·코스·판정·종료 이유·측정 facts·실행 식별 정보 |
| 제약/예산 | 설정 해시, 출발/도착점 변경 정책, 후보 생성 시도 수, 변경 금지 사항 |

SceneGraph는 JSON 형태의 문맥 입력이다. 이 경로는 GNN을 학습하거나 point cloud를
직접 해석하는 방식이 아니다. 모든 과거 rollout의 전체 그래프·영상·시계열을
LLM에게 보내는 것도 아니다. 기준 코스 그래프와 구조화된 결과 요약을 사용한다.

로봇 사양만으로는 실제 실패를 예측하기 어렵기 때문에 정책과 관측 조건을 구분한다.
같은 G1이라도 카메라가 없는 지도 추종 정책과 시각 기반 정책의 취약점은 다를 수 있다.
향후 로봇 VLM을 추가하면 별도 실행 조건으로 정의해야 하며, 현재 결과와 섞지 않는다.

## 4. LLM 출력: 하나의 scene이 아닌 부분 공간

출력에는 다음 항목이 있다.

- `schema_version`: `failure-space-proposal-v2`.
- `config_sha256`: 어떤 사용자 설정을 대상으로 한 제안인지 식별.
- `spaces`: 하나 이상의 부분 공간. 각각 승인된 `layout`, 설명인 `hypothesis`,
  좁혀진 파라미터 범위/선택지인 `domains`로 구성.

설명용 예를 들면 다음과 같다. 실제 관측이나 실제 모델 응답이 아니다.

> ramp_then_obstacles 코스에서 경사각 8–12도와 마찰계수 0.15–0.30을 함께 탐색한다.
> 낮은 마찰과 경사가 결합될 때 진행 정체가 생길 수 있다는 가설을 확인한다.

사용자가 원래 허용한 경사각이 0–12도라면 8–12도는 허용되지만 12–20도는 거부된다.
LLM이 언급하지 않은 다른 허용 축은 기준값에 고정되지 않고 원래 범위에서 추출된다.
`hypothesis`는 사람이 이해할 설명이며, 호스트가 실행하는 코드나 판정 규칙이 아니다.

현재 부분 공간은 각 축의 범위를 조합한 직육면체 형태다. 예를 들어
“경사각이 커질수록 마찰을 선형으로 줄인다” 같은 상관관계 식을 직접 표현하지 않는다.
여러 부분 공간을 제안할 수 있지만 정교한 상관 분포나 인과 모델은 아직 없다.

## 5. 실제로 어떤 후보를 선택하는가?

기본 혼합 모드는 네 번의 **후보 생성 시도**를 다음 순서로 반복한다.

| 슬롯 | 방법 | 목적 |
| --- | --- | --- |
| 1, 2 | 전체 허용 범위에서 추출, 코스를 순환 선택 | LLM이 놓친 조건과 새로운 조건도 탐색 |
| 3 | LLM이 제안한 부분 공간을 순환 선택하고 그 안에서 추출 | 의미 있는 조건 조합에 일부 예산 집중 |
| 4 | 검증된 실패 중 하나를 무작위 선택하여 그 주변에서 추출 | 실패 조건의 주변 변형도 확인 |

실패 이력이 있으면 네 슬롯 기준 50%/25%/25%다. 실패 이력이 없으면 마지막 슬롯도
전체 범위 탐색으로 바뀌므로 75%/25%가 된다. 시도 수가 4의 배수가 아니면 마지막
불완전 묶음 때문에 정확한 비율과 다를 수 있다. 이 비율은 현재 코드에 고정되어 있다.

혼합 모드의 실제 값 추출은 의사난수 기반이다. 정수는 양끝을 포함하는 정수값,
범주형은 허용 선택지, 연속형은 지정 범위의 값을 추출한다.
**현재 v2 혼합 모드는 LLM+Sobol 방식이 아니다.**

실패 주변은 원래 허용 범위 폭의 15%를 반경으로 한다. 정수는 최소 한 단계의
반경을 사용하고 전체 허용 범위를 벗어나지 않도록 자른다. 생성 시드와 범주형
배치 패턴은 좁히지 않는다. 여러 축을 동시에 바꾸므로 엄밀한 한 요인 실험이나
성공/실패 경계의 이분 탐색과는 다르다.

별도 대조군 `random`과 `sobol`은 LLM 제안이나 실패 주변 집중 없이 전체 범위에서
코스를 순환한다. Sobol은 코스별 파라미터 공간을 채우는 수열을 사용한다.
이는 장애물들을 실제 바닥 위에 등간격 배치한다는 뜻이 아니다.

## 6. 제안이 실제 장면이 되는 방식

호스트가 승인된 레시피에 선택된 값을 넣어 SceneSpec을 생성한다. 이 하나의
정의로부터 SceneGraph, 이동 지도, XML을 함께 재생성하고 일관성을 검사한다.

제어 가능한 요소는 경사각/길이, 계단 높이/개수/디딤판, 폭, 마찰,
요철 진폭/간격, 좁은 통로 폭, 장애물 개수/크기 범위/배치 패턴/시드 등이다.
코스 순서는 승인된 템플릿을 선택하여 바뀐다. 임의의 새 토폴로지를 LLM이 직접
발명하거나 모든 장애물의 xyz/회전을 직접 수정하는 기능은 이 경로에 없다.

특히 `size_max_m.2`는 장애물 높이의 상한이지 모든 장애물의 고정 높이가 아니다.
생성 시드는 장애물 배치와 요철의 구체적 형태를 바꾼다. 탐색기 시드와 장면 생성
시드는 다른 역할이며 모두 저장해야 재현 조건을 이해할 수 있다.

현재 예제는 `generated_course_end`를 사용한다. 계단 개수·길이가 달라지면 코스
끝의 도착점도 달라질 수 있다. 각 후보의 실제 출발/도착점을 기록하며, 고정 도착점
실험으로 해석하면 안 된다. `fixed`는 기준 코스와 다른 끝점을 가진 후보를 거부한다.

## 7. 무엇을 실패로 인정하는가?

장면 생성 단계의 `READY_FOR_TERRAIN_RUNNER`는 “실행 가능한 입력”이라는 뜻이다.
로봇 성공도 실패도 아니다. 지도 연결 불가·불가능한 치수 등의 `INVALID_SCENE`도
로봇 실패가 아니다. 정적 지도 검사를 통과했다고 실제 전신 보행이 보장되지는 않는다.

실행 후에는 먼저 실행이 유효한지 확인한다. 현재 feedback 코드는 유효한 실행에서
`navigation_success == false`일 때 `robot_failure == true`로 가져온다.
실행 오류나 판정 불확실 결과는 별도 보존하고 실패 주변 탐색의 출발점으로 쓰지 않는다.
충돌·정체 등의 이유와 측정 facts는 함께 보존하되, LLM 설명만으로 실패 원인을 확정하지 않는다.

다음 라운드에 앞서 설정/장면/요청/실행 자원/코드/산출물 해시를 검사한다.
성공 결과도 LLM 입력에 포함한다. 이력 사용은 프롬프트 문맥을 통한 적응이지
LLM 가중치 업데이트나 ExtraTrees 학습이 아니다.
현재 누적 feedback 상한은 64개이며 자동 이력 요약/선별은 없다.

## 8. 기존 ExtraTrees AFS와의 차이

| 구분 | 기존 수치 대리 모델 기반 AFS | 현재 LLM 기반 v2 |
| --- | --- | --- |
| 주요 역할 | 수치 특징으로 학습한 모델이 지표를 예측 | 문맥과 이력으로 탐색 범위를 제안 |
| 적응 | 관측 자료로 대리 모델 재학습 | 검증된 관측을 다음 요청에 포함 |
| 후보 선택 | 예측·불확실성 등을 사용하는 acquisition | 고정 비율 혼합과 무작위/국소 추출 |
| 출력 해석 | 학습 모델의 수치 예측 | 아직 검증되지 않은 탐색 가설 |

기존 Panda 경로와 G1 로컬 scene-search 파일의 ExtraTrees 구현은 별개다.
현재 v2가 그 모델을 내부적으로 재사용하거나 대체 학습한 것은 아니다.

## 9. 연구 평가에서 주의할 점과 다음 실험

현재 `--samples`는 장면 생성 시도 수다. 같은 수를 넣어도 방법마다 무효율이 다르면
실제 로봇 평가 횟수가 달라진다. Random/Sobol보다 낫다고 주장하려면 같은 유효
rollout 예산과 동일한 로봇·정책·평가 조건으로 다중 시드 비교가 필요하다.

보고할 항목은 유효 실행 수, 실패 수/비율, 최초 실패까지 비용, 실패 유형과 조건의
다양성, 확인 재실행의 재현율, 무효/오류율, 전체 시도 수·시간·LLM 비용이다.
같은 실패를 반복해서 찾았다고 새로운 실패 메커니즘이 늘었다고 해석하지 않는다.
현재 중복 제거는 revision 기반이지 의미적 장면/실패 클러스터링이 아니다.

추가로 LLM의 기여만 분리하려면 향후 동일 혼합 비율에서 LLM 슬롯만 무작위로
대체하는 ablation이 필요하다. 이 비교 모드는 아직 구현되어 있지 않다.

2026-09-13 기록의 116개 테스트 통과와 12개 후보 중 10개 유효 번들은 구현 검증
증거이지 LLM의 실패 발견 우월성 증거가 아니다. 이번 문서화에서는 새 실험을 하지 않았다.
자동 반복 실행, 동일 유효 예산 비교 드라이버, 실패 다양성 자동 평가 등은 남은 작업이다.
