# AFS 설계 논의 정리 — LLM 우선 접근

작성일: 2026-09-13 UTC.
성격: 사용자와의 설계 논의 및 방향 결정 기록. 구현 완료 명세가 아니다.

## 1. 이번에 정한 방향

사용자는 ExtraTrees 기반 지형 AFS를 먼저 완성하기보다 **LLM을 사용하는 AFS부터
시작하는 방향**을 선호한다고 밝혔다. 이 문서는 그 방향을 다음 설계의 출발점으로
기록한다. 이번 요청은 문서 저장이며, API 연결·유료 호출·탐색 실행·코드 구현까지
승인하거나 수행한 것은 아니다.

- 우선 검토할 역할은 **LLM 대리 모델(surrogate)** 이다.
- LLM이 후보를 직접 만드는 역할도 논의했지만, 대리 모델과 후보 생성기를 동시에
  바꿀지는 아직 결정하지 않았다. 두 역할의 효과는 구분해서 평가해야 한다.
- 기존 ExtraTrees 파일럿을 삭제하지 않는다. 추후 비교 기준선으로 활용할 수 있다.
- 특정 외부 모델, API 제공자, 예산, 프롬프트, 평가 점수, 후보 선택 규칙은 미확정이다.
- LLM 대리 모델을 선택했다는 것이 로봇 제어 정책을 LLM/LAM으로 교체한다는 뜻은 아니다.

## 2. AFS의 목적과 공통 흐름

AFS(Active Failure Search)는 로봇·정책·태스크를 고정한 조건에서 환경을 변화시키고,
실제 실행 결과를 이용해 다음 시험 장면을 능동적으로 선택하는 실패 탐색이다.
목표는 보행 모델 개선이나 모든 지형에서의 성공이 아니라, 제한된 예산에서 실패 조건과
성공/실패 경계를 찾아 재현 가능한 회귀 사례와 보고서로 남기는 것이다.

```text
기준 장면 + Task Goal + 변경 허용 범위
                 ↓
초기 후보 생성 → 장면 유효성 검사 → 시뮬레이션 실행
                                      ↓
                              실제 결과와 지표 수집
                                      ↓
                             대리 모델 학습/문맥 갱신
                                      ↓
                           다음 후보 평가·선택 → 반복
```

경사각·계단 높이를 수동으로 바꾸어 보행 한계를 상세 분석하는 실험은 별도 진단이다.
AFS 구현의 필수 선행 작업으로 두지 않는다. 단, 잘못된 기하·판정·실행 오류를 로봇 실패로
집계하지 않도록 최소한의 시스템 검증과 실패 재현성 확인은 유지한다.

## 3. 현재 구현과 향후 설계의 구분

| 항목 | 현재 상태 |
|---|---|
| 기존 Panda AFS | 별도 실행 경로. 8D mutation과 장면 특징을 합한 16D 입력, 여섯 physical margin 예측 |
| G1 장면 탐색 파일럿 | 장애물 하나의 X/Y 이동량을 입력으로 하는 ExtraTrees 적응형 탐색 구현 |
| G1 파일럿 실행 | trusted local bundle 생성·등록 후 navigation@1.0 HTTP 실행. 일반 client method 플러그인과 별개 |
| 다양한 지형 | SceneSpec 기반 경사·계단·마찰·폭·장애물 생성 및 독립 CUDA 실행기 존재 |
| 지형 AFS | 다양한 지형 파라미터를 적응형 탐색 루프에 연결하는 작업은 아직 미완료 |
| LLM 대리 모델 | 논의 및 우선 방향 결정 단계. 구현·API 연동·효과 검증 없음 |
| 일반 그래프 학습 | G1 파일럿이 SceneGraph 자체를 이해하거나 그래프 임베딩을 학습하지는 않음 |

지형 bundle은 기존 내비게이션 서버에서 등록/해석을 차단한다. 공통 서버의 지형 통합은
여전히 미구현이며, LLM 도입을 이유로 이 실행 경계를 무시하지 않는다.

## 4. AFS의 입력과 SceneGraph의 역할

**AFS 시스템의 입력**과 **대리 모델의 입력 표현**은 다르다.
시스템 입력 계약의 제안은 다음과 같다.

1. 기준 SceneGraph와 실제 기하를 나타내는 SceneSpec.
2. Task Goal: 출발·목표, 성공 조건, 허용/금지 접촉 등 평가에 필요한 조건.
3. 변경 제약: 수정 가능한 객체/속성, 수치 범위, 고정 요소, 장면 유효성 규칙.
4. 과거 실험 이력: 실제 후보 조건, 평가 결과, provenance.

현재 생성기에서는 SceneSpec이 원본이고, SceneGraph·이동 지도·물리 XML을 함께 파생한다.
그래프만 수정하고 물리 기하를 그대로 두는 방식은 사용하지 않는다. 새 후보는 새 revision을
가지며 객체 ID·좌표·단위·revision이 파생 산출물 간 일치해야 한다.

SceneGraph의 노드·간선·속성으로 객체와 관계를 표현할 수 있지만, 거리·경로·간격의 정확한
수치는 기하/이동 지도에서 계산해야 할 수 있다. 목표와 무관한 경사를 위험 요소로 과대평가하지
않도록 Task Goal과 목표 경로 정보를 함께 다루는 것이 중요하다.

### ExtraTrees용으로 논의한 표현

일반적인 ExtraTrees는 그래프 JSON을 직접 입력받는 모델이 아니다. 고정 길이 숫자 벡터가
필요하다. 예를 들어 환경 변경 파라미터에 다음과 같은 특징을 추가할 수 있다.

- 목표 경로상의 최소 통로 폭, 최대 경사, 최소 마찰, 최대 단차.
- 기준 경로 길이, 회전 횟수/각도, 장애물과 경로의 최소 간격.
- 필요하면 고정되지 않은 로봇/태스크 조건.

이는 후보 특징 설계이며 현재 G1 파일럿에 모두 구현된 것은 아니다. 최솟값·최댓값만 사용하면
‘경사 다음 좁은 통로’와 ‘좁은 통로 다음 경사’ 같은 순서 차이를 잃을 수 있다. 구간별 특징,
GNN 또는 LLM은 확장 선택지로 논의했으며 GNN 도입은 결정하지 않았다.

### LLM용으로 논의한 표현

SceneGraph를 구조화 JSON 또는 텍스트로 직렬화해 제공할 수 있다. 단위와 좌표계, 객체 ID,
관계, 변경 가능한 속성, Task Goal, 후보 파라미터, 과거 실험 결과를 명시한다.
거대한 원시 mesh/point cloud 전체를 LLM에 넣는 설계는 아니다.

LLM이 문장을 읽을 수 있다는 사실이 정확한 공간/물리 추론을 보장하지 않는다. 기하 검사와
수치 계산은 결정적인 코드로 수행하고, LLM 예측은 실제 rollout으로 검증한다.

## 5. 기존 ExtraTrees 파일럿의 정확한 설계

구현: `src/procedural_world/search.py`, 프로토콜: [G1_SCENE_SEARCH.md](G1_SCENE_SEARCH.md).

- 입력: 검증된 기준 장면의 obstacle_0 이동량 두 개. X [-2, 2] m, Y [-2.4, 2.4] m.
- 초기 탐색: 유효 관측 네 개까지 Sobol.
- 모델: ExtraTreesRegressor, 트리 64개. 유효 결과가 추가될 때마다 다시 학습.
- 후보: 매번 2D 정규화 공간에서 무작위 후보 512개 생성.
- 최소화할 acquisition: 예측 평균 − 트리 간 표준편차 − 0.1 × 최근접 기존 시도와의 거리.
- 무효 장면은 학습 대상에서 제외하지만, 제안 이력의 거리 계산에는 포함.

현재 scalar utility는 다음과 같은 탐색용 휴리스틱이다.

```text
성공: max(0.001, 1 - 실행 시간 / 최대 실행 시간)
실패: -1 - min(남은 목표 거리 / 10, 1)
무효 실행 또는 필요한 지표 누락: 학습 관측 없음
```

작은 값이 실패 쪽이다. 성공 중에는 시간 여유가 적은 결과를, 실패 중에는 남은 거리가 큰
결과를 낮게 평가한다. 트리 간 편차는 근사적인 탐색 신호이지 보정된 확률/신뢰구간이 아니다.
이 utility는 Panda의 여섯 margin이나 물리적 안전 인증 점수가 아니며, 지형 AFS에 그대로
채택하기로 확정하지 않았다. 충돌·정체를 한 숫자로 합칠 때 잃는 정보도 검토해야 한다.

## 6. LLM 대리 모델 접근의 제안

첫 출발점은 외부 LLM에 과거 실험을 문맥으로 제공하고, 아직 실행하지 않은 후보의 평가
점수나 실패 유형을 예측시키는 것이다. 별도 미세학습은 필수라고 정하지 않았다.

```text
Task Goal + 후보 SceneGraph/파라미터 + 실제 과거 관측
                         ↓
                    LLM 결과 예측
                         ↓
                  후보 선택 규칙 적용
                         ↓
             실제 시뮬레이션과 고정된 평가기
                         ↓
                  관측 이력에 결과 추가
```

이때 구분할 역할:

| 역할 | 의미 | 논의 상태 |
|---|---|---|
| 대리 모델 | 주어진 후보의 실행 결과를 예측 | LLM 우선 검토 대상 |
| 후보 생성기 | 다음에 시험할 파라미터/장면을 제안 | 별도 변형으로 검토 가능, 미확정 |
| 평가기 | 실제 실행이 성공/실패인지 판정 | 시뮬레이션 지표와 고정 규칙 유지 |
| 로봇 정책/LAM | 로봇의 행동을 생성 | 이번 LLM 대리 모델 도입과 별개 |

기대 가설은 수치뿐 아니라 장면 의미·관계와 적은 초기 관측을 활용해 더 유용한 후보를
고를 수 있다는 것이다. 이는 우리 환경에서 아직 입증되지 않았다. 예측 설명 역시 물리적
원인으로 확정하지 않는다. 실험하지 않은 LLM 추정치를 실제 관측처럼 이력에 넣지 않는다.

## 7. 아직 확정하지 않은 설계 항목

- 첫 탐색 장면의 구조와 허용 변수: 고정된 구성에서 수치부터 바꿀지, 구성 자체도 바꿀지.
- LLM 입력 스키마와 과거 이력 선택/요약 방식, Task Goal 표현.
- 예측 대상: scalar utility, 실패 유형, 연속 지표, 순위 중 무엇을 사용할지.
- 후보 선택과 exploration: LLM의 자기 보고 확률/확신을 그대로 신뢰하지 않는 방법.
- 모델/버전, 호출 비용·시간 상한, 응답 스키마·범위 검사, 실패/재시도 처리.
- 실행 경로: 독립 지형 runner를 탐색 orchestration과 어떻게 연결할지.
- 상태 저장/재개, API 응답 캐시, 프롬프트·모델·요청·응답 provenance.
- 외부 제공자에게 보낼 데이터 범위 및 인증정보 관리.

특히 ‘실패 확률 90%’라는 LLM 출력이나 여러 응답의 편차는 자동으로 보정된 불확실성이
되지 않는다. 불확실성을 쓰는 acquisition은 별도 설계·검증이 필요하다. temperature를
고정해도 외부 모델 서비스의 완전한 재현성을 보장한다고 주장하지 않는다.

## 8. 비교 실험의 제안과 유지할 원칙

Random/Sobol과 기존 ExtraTrees를 기준선으로 유지하고 LLM 기반 탐색을 추가하는 비교를
논의했다. 이것은 LLM 구현 전에 ExtraTrees 지형 확장을 먼저 완성해야 한다는 뜻이 아니다.

대리 모델의 효과를 분리하려면 같은 초기 관측, 탐색 범위, 후보 생성 방식, 예측 목표,
가능한 한 같은 후보 선택 규칙을 사용한다. 초기 이후 각 방법은 자신이 실행한 결과로
이력을 갱신한다. 이후 제안 이력은 서로 달라지므로 모든 단계에서 동일 이력을 강제하지 않는다.
입력 표현도 다르게 제공한다면 결과를 순수 모델 차이로만 해석하지 않는다.

LLM 후보 생성까지 포함한 방법은 별도의 비교군/분해 실험으로 둔다. ‘LLM 사용’만으로
AFS가 되는 것은 아니며 실제 관측 피드백으로 다음 선택이 변하는지 확인해야 한다.

공통 원칙:

- 로봇·정책·제어기·평가 기준·실행 조건을 비교 중 고정.
- 같은 **유효 평가 rollout 예산**, 별도의 총 제안/재시도/시간 상한.
- 생성 무효, 수치 불안정, 인프라 오류와 유효한 로봇 실패를 분리.
- 실패 발견 수, 최초 실패 비용, 재현율, 무효율, 시간 및 LLM 호출 비용을 함께 기록.
- 고유 실패 유형은 단순 실패 횟수와 구분하고 별도 정의 없이 주장하지 않음.
- 실험 도메인 결정에 쓴 자료와 최종 평가 자료를 구분하고 여러 seed/장면에서 확인.
- LLM의 우월성을 미리 결론 내리지 않음. 모든 기존 실패와 산출물 보존.

로그·장면·요청·결과·영상·재현 정보는 `/workspace/g1_failure/runtime` 아래 새 실행
경로에 저장하는 기존 원칙을 유지한다. 세부 LLM 실험 폴더 규약은 아직 정하지 않았다.

## 9. 다음 설계 순서

1. 실제 worker 접촉 로그 검증을 마무리하되 별도의 보행 개선 실험으로 확대하지 않음.
2. LLM-first AFS의 작은 첫 입력/출력 계약, 평가 목표, 탐색 도메인을 확정.
3. 유효성 검사·호출 실패 처리·이력 저장을 갖춘 LLM 예측/선택 경로 구현.
4. 관측 결과가 다음 선택에 반영되는 작은 end-to-end 실험 확인.
5. 공정한 기준선 비교를 구성하고 효과와 한계를 보고.

이번 문서 저장은 위 작업들의 구현 완료를 의미하지 않는다.

- [현재 G1 파일럿](G1_SCENE_SEARCH.md): 구현된 2D 장애물 탐색과 주장 경계.
- [지형 생성/실행](TERRAIN_SCENES.md): 지형 생성과 독립 실행 경로. 해당 문서의 과거
  guard 미적용 문구는 이후 사용자 적용 및 검증 기록과 구분해서 읽어야 함.
- [LLAMBO, ICLR 2024](https://arxiv.org/abs/2402.03921): 문맥 내 학습을 이용한 LLM
  surrogate/candidate sampling 선행 사례. 하이퍼파라미터 최적화 결과를 G1 실패 탐색
  효과로 직접 확대 해석하지 않음.
- [GOLLuM, Nature Machine Intelligence 2026](https://www.nature.com/articles/s42256-026-01283-z):
  언어 표현과 GP 기반 불확실성을 결합한 실험 최적화 연구. 일반 LLM API에 확신을
  질문하는 것과 같은 방법이 아니며, 우리 구현으로 채택한 것은 아님.

위 연구는 이전 대화에서 확인한 참고 자료이며, 이번 문서는 추가 문헌 조사 보고서가 아니다.
