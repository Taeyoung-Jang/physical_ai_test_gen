# GPT-6 기반 장애물 제거 후 이동: 작업 계획

작성일: 2026-09-15 UTC. 상태: 제안된 구현 계획, 아직 구현/검증 완료가 아님.
목표는 실제 로봇 하드웨어가 아닌 G1/MuJoCo 시뮬레이션에서 시작한다.

## 1. 첫 목표와 비목표

첫 시나리오: 평지 통로를 막은 이동 가능한 상자 하나를 지정된 옆 공간으로
밀어 경로를 연 뒤 G1이 목표점에 도착한다. GPT-6는 판단과 행동 선택을 담당하고,
검증된 로컬 실행기가 접근·밀기·정지·보행을 수행한다.

첫 완료 산출물은 환경 그림만이 아니라 실제 접촉·물체 이동·로봇 통과가 보이는
MP4, 요약 GIF, 전후 지도, 행동 타임라인과 판정 보고서다. 실패 영상도 보존한다.

처음부터 집기/운반/손가락 파지, 임의 미로, 다중 물체 연쇄 조작, 계단 위 밀기,
실물 배포, 새 VLA 학습을 포함하지 않는다. 범용 조작 가능성을 주장하지 않는다.
물체 위치 직접 변경/순간이동/상자에 외부 힘 직접 주기를 로봇 밀기로 세지 않는다.

## 2. 현재 확인한 재사용 범위와 결손

- 기존 CUDA GR00T 보행, 지도 추종, MuJoCo 실행/기록은 재사용 후보다.
- `groot_locomotion.py`는 정책 action 이후의 관절을 0 자세 PD로 유지한다.
  현재 경로에는 상체 조작 목표를 실행하는 기능이 없으므로 별도 제어 통합이 필요하다.
- 로컬 GR00T-WholeBodyControl에는 decoupled_wbc와 관련 문서가 존재한다.
  설치된 자산/의존성/라이선스/로봇 모델/관절 순서의 실제 적합성을 먼저 확인한다.
  파일이 존재한다는 사실은 우리 runner에서 조작에 성공했다는 증거가 아니다.
- 기존 terrain_worker는 벽 및 비발 접촉에 충돌 판정을 적용한다.
  의도된 손-상자 접촉까지 실패로 세지 않도록 별도 task/evaluator가 필요하다.
- 정적 bundle의 출발-도착 경로 필수 조건은 이 작업과 맞지 않는다.
  기존 navigation/terrain 판정·파일 형식을 전역 완화하지 않는다.
- 기존 GPT-6 AFS의 live 구조화 제안 성공은 확인됐지만 로봇 VLM 실행은 미구현이다.

## 3. 구조와 관측 계약

```text
AFS GPT-6 → 시험 환경 생성 → 시뮬레이터
                               ↓ 허용된 관측
                         로봇 GPT-6 판단
                               ↓ 제한된 행동 요청
                   유효성 검사 + 로컬 행동 실행기
                               ↓
                    상체 조작 / 균형 / CUDA 보행
                               ↓
                       관측 갱신 및 실제 평가
```

AFS와 로봇은 같은 모델을 사용해도 프롬프트·상태·예산을 분리한다. AFS의 실패 가설,
미래 판정, 평가용 숨은 물성을 로봇 프롬프트에 전달하지 않는다. 로봇의 관측 허용
범위를 명시하고 `unknown`인 질량 등을 LLM이 확인된 사실로 주장하지 않게 한다.

첫 조건은 전체 지도 + GT 로봇/물체 위치를 제공하는 명시적 GT 조건이다. 이후 같은
전체 지도를 유지하면서 카메라 프레임을 추가한 VLM 조건을 별도 버전으로 시험한다.
전체 지도를 제거하거나 SLAM 개발을 선행시키지 않는다. GT 위치를 계속 제공하면
시각 기반 localization을 검증한 것으로 주장하지 않는다.

로봇 입력: 목표, 지도/SceneGraph의 허용된 부분, 현재 pose/물체 상태, 관측 시각과
state_version, 사용 가능한 행동과 한계, 직전 행동 결과. VLM 조건에는 카메라
내·외부 파라미터와 타임스탬프가 연결된 이미지도 포함한다.

출력 행동 계약(제안): `navigate_to`, `push_object`, `observe`, `stop`.
객체 ID, 지도 좌표계, 목적 pose 또는 push goal, 사전조건을 typed schema로 제한한다.
완료/실패는 LLM 선언이 아닌 실행기가 확인한다. 없는 객체·허용되지 않은 이동 영역·
과도한 이동량·지원하지 않는 행동은 실행 전에 거부한다. `pick/place`는 아직 광고하지 않는다.

LLM 응답을 기다리는 동안 로컬 균형 제어는 계속 작동해야 한다. LLM을 물리 시뮬레이션
매 step에서 호출하지 않는다. 행동 완료/실패/상태 변화 때 호출하며 오래된 state_version
명령은 거부하고 재관측한다. 타임아웃·호출 상한 시 안전 정지/명시적 실패로 종료한다.

## 4. 단계별 작업과 통과 기준

### P0. 계약 및 조작 실행 가능성 확인

- 실제 로봇 XML의 손 접촉 형상, 팔 자유도/limit, ONNX 관절 매핑을 점검.
- 상체 목표 제어와 기존 보행의 결합 가능성, decoupled WBC 재사용 비용을 비교.
- 로봇/물체 joints는 이름과 qpos/dof 주소로 매핑한다. 동적 상자 freejoint 추가 후
  기존 하드코딩 인덱스가 로봇 상태를 잘못 읽지 않는지 회귀 검사한다.
- 신규 `clear_path` task, 관측/행동 schema, success/invalid/infra 분류를 정한다.
- 원인 확인용 API 오류 코드·request ID·stage를 안전하게 남기는 공통 기록을 설계한다.

통과: 사용할 제어 경로와 손 접촉 모델의 근거가 있고, 상자 추가 전후 보행
관절/관측 매핑이 일치한다. 제어가 불가능하면 필요한 외부 구성요소와 범위를 먼저
보고한다. 단순한 GPT 프롬프트 변경으로 이 관문을 넘겼다고 간주하지 않는다.

### P1. 동적 장면과 시각 보고서

- 평지/통로/옆 빈 공간/상자 1개의 deterministic fixture를 만든다.
- 상자 질량·관성·마찰·충돌, 정적 벽, movable/forbidden 속성을 구분한다.
- 기준 scene revision은 고정하고 실행 중 물체 pose/그래프/지도는 시간별 상태로 기록.
- 초기 경로 없음은 허용하되 배치 겹침·목표 부재 등 구조적 무효는 분리한다.
- 3D 전체 장면, 로봇 시점, 지도/물체 전후 위치를 기록하는 HTML 보고서 골격을 만든다.

통과: 초기 장면을 눈으로 확인할 수 있고, 물리와 SceneGraph/지도 ID가 일치한다.
동적 물체 단위 검사는 가능하지만 외부 힘 검사를 로봇 조작 성공 증거로 쓰지 않는다.

### P2. LLM 없이 밀기 행동 검증 — 핵심 기술 관문

- 고정 스크립트로 접근→정지/정렬→손 접촉→짧은 밀기→분리→경로 갱신→통과.
- 실제 로봇 actuator와 접촉으로만 물체를 움직이고 전도/과도 접촉/무진행을 감시한다.
- 허용 접촉은 지정된 작업 단계·손 링크·대상 물체에 한정한다. 벽 충돌/몸통 충돌 등은
  별도 실패이며 단순히 모든 충돌 검사를 끄지 않는다.
- 밀기 목표 영역 도달/경로 개방/안전한 최종 이동을 별도로 판정한다.

통과: 고정 fixture의 반복 결과와 MP4/GIF가 있고, 성공 시 로봇 접촉에 의한 물체
이동과 실제 통과를 확인할 수 있다. 같은 시드 반복만으로 일반 성공률을 주장하지 않는다.
이 단계가 실패하면 제어 범위를 한정하거나 재사용 경로를 재검토하고 GPT 실험을 확대하지 않는다.

### P3. GPT-6 상위 계획 연결

- 실제 검증된 행동만 도구/구조화 출력으로 노출한다.
- GT 조건에서 지도·상자·목표를 보고 다음 행동을 선택하고 실행 결과로 재계획한다.
- API 실패·거부·형식 오류·없는 객체·무한 재시도·오래된 관측을 mock 테스트한다.
- 최초 live 실험 전에 호출 횟수/토큰/시간 상한을 고정한다. 구체 상한은 P0에서
  실행 지연과 비용을 확인해 정하며 무제한 호출하지 않는다.

통과: 실제 GPT 응답→행동 실행→상자 이동→통과가 하나의 기록으로 연결되고,
스크립트 제어 결과와 구분된다. 이 단계가 첫 GPT 기반 end-to-end 시연이다.

### P4. 카메라 기반 VLM 조건

- GPT-6에 실제 로봇 카메라 프레임을 제공하고 map-frame 객체 ID와 연결한다.
- 매 관측의 GT 제공 항목과 영상에서 추정한 항목을 구분한다. 영상만으로 힘/질량을
  확정하지 않는다. 영상이 추가되었다는 이유만으로 VLA/저수준 시각 제어라고 부르지 않는다.
- 시각 없는 GT 조건과 비교해 이미지 사용·가림·객체 구분·재관측 효과를 확인한다.

통과: 프레임과 판단 시각을 보고서에서 대조할 수 있고 입력 조건별 성과를 분리한다.

### P5. 조작 가능한 공간의 AFS 통합

- 새 scene domain에 상자 위치/크기/질량/마찰, 통로 폭, 옮길 공간 등을 추가.
- 기존 정적 경로 필터와 분리: 초기 경로 없음, 계획상 제거 가능, 제거 가능성 불명,
  명백한 생성 무효를 구분한다. 기하적 제거 가능성이 실제 G1 조작 성공의 증명은 아니다.
- known-feasible fixture와 스크립트 기준선을 우선 사용하고 불가능한 장면만 반복 생성해
  실패율을 높이는 현상을 막는다. 일반 장면의 조작 가능성 oracle은 미해결 연구 항목이다.
- AFS GPT와 로봇 GPT 사이 정보 누출을 검사한다. LLM AFS/Random/Sobol을 동일
  유효 평가 예산·고정 로봇/정책/판정·다중 시드 조건으로 비교한다.
- AFS와 로봇 LLM은 서로 다른 실험 축이다. AFS 효과 비교에서는 로봇 정책을 고정하고,
  로봇 LLM 효과 비교에서는 같은 장면 집합을 사용한다.

통과: 실제 실패 영상과 유효/무효/오류/호출비용/반복 재현 결과가 연결된 비교 보고서.
실패 원인은 우선 관측 증거에 따른 범주이며 인과 확정에는 재실행/요인 분리가 필요하다.

## 5. 완료 판정과 보고 형태

성공: 목표 영역 도착 + 요구된 경로 개방 + 낙상/금지 접촉 없음 + 유효한 실행.
시간 초과, 잘못된 행동 선택, 무진행 밀기, 물체의 금지 영역 진입 등을 구분한다.
적절한 중단이 정답인 시나리오는 별도 task 계약으로 두고 도착 과제와 점수를 섞지 않는다.

매 실험에 `report.html` 하나로 다음을 제공하는 것을 요구한다.

- 실제 실행 여부 및 입력 조건(GT/VLM/스크립트), 최종 판정과 짧은 설명.
- scene 3D 미리보기, MP4, 요약 GIF, 초기/최종 지도.
- 로봇과 상자의 실제 궤적, 의도된 계획과 실제 행동의 차이.
- GPT 입력 이미지/행동 출력, 실행 결과, 접촉 이벤트 타임라인.
- model/prompt/controller/evaluator/assets revision, API usage·시간·오류, 재현 명령.

런타임 기본 위치 제안: `/workspace/g1_failure/runtime/clear_path/`.
API 키나 전체 인증 헤더는 저장하지 않는다. 실패·초기 시도도 덮어쓰지 않는다.

## 6. 실행 범위 관리

독립된 task/runner/모듈로 시작하고 기존 stand/locomotion/navigation/terrain과
Panda 경로, g1-local-nav를 변경하지 않는다. 공통 파일 변경이 필요한 지점은 별도
회귀 검사 및 검토 대상으로 삼는다. 기존 bwrap 편집 제약이 남으면 숨기거나 전체
파일 교체로 우회하지 않고 해당 변경을 명확히 보고한다.

지금 요청 범위는 계획 수립이다. 위 단계의 API 호출·GPU 실험·모델 다운로드·제어
코드 변경은 이번 작업에서 하지 않았다. 먼저 P0–P1을 구현하고 P2 검증 결과로
다음 단계의 세부 일정과 범위를 확정하는 순서를 제안한다.
